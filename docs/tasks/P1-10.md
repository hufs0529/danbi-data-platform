# P1-10 오케스트레이션(MWAA Airflow 3)과 계보(OpenLineage → Marquez)

## 목표

배치·이벤트 기반 파이프라인을 하나의 운영 화면에서 돌리고, 모든 실행이 계보를 남기게 한다(FR-11, S-G1). 실패 알림에는 런북 링크가 붙는다.

## 설계 포인트

- **무거운 일은 MWAA 밖에서.** 워커는 EMR·ECS 를 부르고 기다리기만 한다(지연 가능 연산자로 슬롯 반환). mw1.micro(동시 3)로 충분한 이유다.
- **파싱 시점에 AWS 호출 금지.** 설정은 Airflow Variable(SSM 백엔드)을 템플릿으로 실행 시점에 푼다. 트리거처럼 파싱 시점에 필요한 큐 URL 은 MWAA 사용자 설정(`danbi.*`)에서 환경변수로 읽는다.
- **이벤트 기반 스케줄.** 정산 파일은 언제 올지 모른다. 폴링 센서 대신 SQS 를 감시하는 AssetWatcher 로 도착 즉시 실행한다. 재전송은 버전 ID 가 달라 둘 다 적재기로 가고, 적재기가 내용 해시로 판정한다.
- **dbt 테스트 실패는 재시도하지 않는다.** 같은 결과가 나올 뿐이다. 실패 = 게시 보류 + 알림.
- **계보 3중 수집.** Airflow(태스크 inlets/outlets), dbt(dbt-ol, 컬럼 계보), Spark(OpenLineage 리스너, MERGE 입출력). Marquez 하나로 모인다.
- **Marquez DB 를 결제 RDS 에 둔 것은 dev 절충이다.** 운영에서는 계보 메타데이터를 소스 DB 와 같은 인스턴스에 두지 않는다(장애·권한 영향 분리).

## 적용

```bash
make db-migrate ENGINE=postgres            # marquez DB·계정 추가
make init STACK=p1-50-orchestration && make plan STACK=p1-50-orchestration && make apply STACK=p1-50-orchestration  # MWAA 생성 20~30분
make dags
# UI: 운영 EC2 로 MWAA 웹서버 VPC 엔드포인트 포트 포워딩 후 https://localhost:8443
aws mwaa get-environment --name danbi-dev --query Environment.WebserverUrl
```

## 검증

- 로컬: `pytest p1/orchestration` (Airflow 가 설치돼 있으면 DagBag 까지)
- MWAA: `p1_silver_merge` 성공 → Marquez UI 에서 `bronze.cdc_events → silver.orders → gold_audit.fct_order_items → gold.fct_order_items` 경로 확인(S-G1: 3번 클릭 안에 원천 컬럼)

## 완료 기준

- 7개 DAG 가 import 오류 없이 올라오고, 정산 파일 업로드 1분 안에 `p1_pg_settlement` 가 시작된다.
- 실패 시 SNS 메시지에 DAG·태스크·로그·런북 링크가 있다.
