# P1-09 PG 정산 파일 적재와 3단계 대사

## 목표

국내 커머스·핀테크에서 가장 자주 쓰는 일, **대사**를 자동화한다. 재무팀이 매일 09:00 KST 에 "어제 매출과 PG 정산 차이"를 원인 코드와 함께 받는다(S-B2, FR-06, NFR-03). 잘못된 파일은 절대 Silver 에 들어가지 않는다(F-06).

## 대사 3단계

| 단계 | 비교 | 주기 | 실패 시 |
| --- | --- | --- | --- |
| 1 소스 vs 레이크 | 창 안 갱신 행 수·금액 합 | 매시 | `SourceLakeMismatch` 알림 → F-01·F-03 런북 |
| 2 Silver vs Gold | Gold 순매출을 Silver 에서 재계산 | Gold 빌드마다 | dbt 테스트 실패 → 게시 중단(P1-08) |
| 3 내부 vs PG | (payment_key, 구분) 금액 합 | 정산 파일 도착 시 + 매일 08:30 | `UnexplainedCount > 0` 즉시 알림 |

## 원인 코드

| 분류 | 원인 | 설명됨 | 의미 |
| --- | --- | --- | --- |
| INTERNAL_ONLY | TIMING_NEXT_DAY | 예 | 23:30 마감 경계 거래가 다음 날 파일에 있다 |
| INTERNAL_ONLY | PG_PENDING | 보류 | 다음 날 파일이 아직 없다 → 내일 재판정 |
| INTERNAL_ONLY | PG_MISSING | 아니오 | PG 누락 → PG 사에 문의 |
| PG_ONLY | TIMING_PREV_DAY | 예 | 내부는 전날 정산일로 분류 |
| PG_ONLY | INTERNAL_STATUS_LAG | 아니오 | 결제는 있는데 내부 상태 미반영(CDC 지연·누락 의심) |
| PG_ONLY | UNKNOWN_TXN | 아니오(위험) | 내부에 없는 거래 → 즉시 에스컬레이션 |
| AMOUNT_MISMATCH | AMOUNT_DIFF | 아니오 | 금액 차이 → 정정본 요청 |

## 설계 포인트

- **생성기와 적재기가 서로를 검증한다.** 테스트가 `p1/generator/settlement.py` 의 결함 파일(중복·정정·인코딩·헤더 v2·잘림)을 그대로 적재기에 넣어 판정을 확인한다.
- **중복은 이름이 아니라 내용 해시로.** 같은 이름의 정정본과 진짜 재전송을 구별한다. 정정본은 차수가 높은 파일이 유효본.
- **부분 적재 금지.** 행 하나라도 형식 오류면 파일 전체를 격리한다. 일부만 들어가면 대사가 거짓으로 일치한다.
- **v1 헤더는 부가세를 분리할 수 없다.** 추측하지 않고 `vat = NULL` 로 둔다.
- **멱등.** 라인은 파일 해시 단위, Silver·대사 결과는 정산일 단위 덮어쓰기. 몇 번 돌려도 같다(로컬 Iceberg 카탈로그로 테스트).
- **도착 이벤트 큐는 SSE-SQS.** 메시지는 버킷·키뿐이다. KMS grant 는 서비스 주체(events)에 줄 수 없어 고객 관리형 키를 쓰려면 키 정책을 열어야 한다.

