# P1-13 접속기록·점검과 탈퇴 파기 워크플로(crypto-shredding)

## 목표

법이 요구하는 것을 시스템으로 바꾼다. 개인정보 조회는 누가·언제·어디서·무엇을 했는지 2년간 위·변조 없이 남고(제8조, NFR-10, S-G3), 대량 조회는 탐지되며(F-10), 탈퇴 회원은 5일 안에(내부 SLO 72시간) 전 계층에서 파기되되 법정 보존 거래 기록은 분리 보관된다(S-G4, FR-14).

## 파기와 보존의 충돌 해결

| 데이터 | 처리 | 이유 |
| --- | --- | --- |
| 회원·배송지·등급 이력·클릭·dim_member | 행 삭제 | 목적 달성(탈퇴) → 지체 없이 파기 |
| 주문·결제·쿠폰 사용·fct_* | member_token → `erased` | 거래 사실(금액·일시)은 남겨 과거 매출이 소급해 바뀌지 않게 한다 |
| 위 거래와 회원의 원래 연결 | `retention.*` 로 복사(별도 버킷·PII 키·법무 역할만) | 전자상거래법 시행령 제6조(5년), 동의 철회 고객 별도 보존 |
| CS 문의 | 분리 보관 후 본문 제거 | 분쟁 처리 기록 3년 |
| 이름·주소 암호문(모든 계층·스냅샷·백업) | 회원 키 폐기(묘비) | 불변 저장소에서의 파기 |
| Bronze 원본 로그 | 행 삭제 + 스냅샷 만료 | 토큰이 남은 원본 |
| P2 검색 인덱스·캐시 | `member.erased` 이벤트 | 파생물 전파(P2-10) |
| Kafka 원문 | 토픽 보존 ≤ 72시간 | SLO 안에서 자연 소멸 |

## 접속기록 위·변조 방지

`chain(d) = sha256(chain(d-1) + sha256(file(d)))`. 어느 날 파일을 고치거나 지우면 그 뒤 체인이 모두 달라진다. 파일·체인 모두 객체 잠금(2년) 버킷에 있고, 매주 월요일 `verify` 가 전체를 다시 계산한다. 감사 요청(S-G3 "특정 회원을 누가 조회했나")은 접속기록의 `subject_tokens` 로 1시간 안에 답한다.

## 실행

```bash
make apply STACK=p1-60-governance && python -m p1.lakehouse.migrate apply   # retention 테이블
aws lambda invoke --function-name danbi-dev-access-log --payload '{"mode":"daily","date":"2026-10-29"}' out.json
aws lambda invoke --function-name danbi-dev-access-log --payload '{"mode":"verify"}' out.json
# 탈퇴 → 매시 자동. 수동 시작
aws stepfunctions start-execution --state-machine-arn <arn> --name erase-<token> \
  --input '{"request_id":"erase-<token>","member_token":"<token>"}'
```

## 완료 기준

- 탈퇴 → `VERIFIED` 까지 72시간 이내, 검증 쿼리 0건, 대장 기록, P2 로 이벤트 전달.
- 체인 검증 OK, 분석가의 대량 조회 시도가 월간 리포트와 알림에 나온다(F-10).
