# P1-11 실시간 매출(속보치)과 이상결제 탐지

## 목표

마케팅팀이 타임세일 중 1분 단위 매출을 보고(S-B1, 이벤트 → 대시보드 p95 ≤ 90초), 리스크팀이 도용 카드 패턴을 10초 안에 받는다(S-B3). 늦은 이벤트(F-05)와 상태 있는 잡 업그레이드(F-09)를 규칙으로 다룬다.

## 산출물

## 설계 포인트

- **속보치와 확정치를 섞지 않는다(ADR-11).** 실시간 값에는 `label=속보치`, `revision` 이 붙는다. 확정치는 다음 날 Gold. 대시보드에 둘을 구분해 표시한다.
- **허용 지연 2분 안의 늦은 이벤트는 창을 다시 내보낸다(revision+1).** 소비자는 window_start 로 덮어쓴다(Iceberg upsert). 그보다 늦으면 `rt.late_events` 로 빼고, 확정치는 Silver 에서 다시 계산하므로 100% 반영된다(F-05).
- **이상결제는 이벤트 시간으로 판단한다.** 10분 전 이벤트가 늦게 와도 5분 창이 맞지 않으면 묶지 않고, 늦게 왔지만 같은 창이면 탐지한다(테스트로 고정).
- **중복 알림 대신 쿨다운.** 같은 카드 5분 안 두 번째 알림은 보내지 않는다. Kafka·Lambda 는 최소 한 번이라 배치 안에서 alert_id 로 한 번 더 거른다.
- **uid 고정(F-09).** uid 가 바뀌면 스냅샷 상태를 복원하지 못해 카드 이력이 사라지고 중복 알림이 난다.
- **Athena 는 Iceberg 기본키를 만들 수 없다.** upsert 대상 `rt.sales_1m` 은 Flink 가 PRIMARY KEY 로 직접 만든다.
- **null 금액은 버리지 않고 센다.** F-08 의 조기 신호(`NullAmounts1m` 지표).

## 검증

- 단위: 집계·중복 제거, 규칙(3곳·쿨다운·창 밖·순서 역전·같은 주소 반복), **생성기가 주입한 도용 카드 100% 탐지·정상 카드 오탐 0**, Lambda 파싱
- AWS: `python -m p1.generator.cli run --faults fraud=0.002` → 리스크 SNS 구독 메일 수신, CloudWatch `Danbi/Realtime NetSales1m`
- F-09: 앱 코드 업데이트(스냅샷 자동 생성) 후 같은 카드로 3번째 결제 → 알림 1건(상태 유지), 중복 0

## 완료 기준

- 탐지 지연(`detection_lag_ms`) p95 ≤ 10초, 대시보드 지연 p95 ≤ 90초, 다음 날 확정치와 차이 ±1% 이내.
